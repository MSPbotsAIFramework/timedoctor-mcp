## Product design

### Goals / Non-goals

**Goals**
- Let an agent, given a Time Doctor credential supplied by the end customer, list the Time Doctor companies/workspaces that credential can see.
- Let an agent list the team members and the projects in a given Time Doctor company.
- Let an agent pull raw time-tracking entries (worklogs) for a date range, optionally narrowed to one user.
- Let an agent pull aggregated productivity-activity numbers for a date range: an overall summary (time worked / manual time / productive vs. not) and a breakdown by application/website category.
- Every call is isolated per request: one customer's data and credential must never appear in another customer's response, even when the service is handling many tenants' calls concurrently.

**Non-goals (v1)**
- No write operations: no creating/editing time entries, no managing users, projects, tasks, invitations, payroll, or directory sync. The ticket asks to "track" activity, not to administer the account.
- No absence/lateness reporting, no disconnectivity reports, no software-cost insights. These are real Time Doctor capabilities but nobody asked for them; adding them speculatively would be scope creep (see "Decisions made by DEV01").
- No OAuth app flow, no token refresh handled by the service (see "Decisions made by DEV01" for why).

### Acceptance criteria AC1..AC10

- **AC1** — Given a valid Time Doctor credential, When the agent asks "what companies/workspaces can I see", Then the tool returns the list of companies that credential has administrative access to (id and name for each).
- **AC2** — Given a valid credential and a company, When the agent asks for the team roster, Then the tool returns the users in that company (id, name, role), paginated, with an optional name/role filter.
- **AC3** — Given a valid credential and a company, When the agent asks for the project list, Then the tool returns the company's projects (id, name, status), paginated.
- **AC4** — Given a valid credential, a company, and a date range, When the agent asks for time-tracking entries (optionally for one user), Then the tool returns the worklog entries in that range, paginated; omitting the user returns entries for the whole company.
- **AC5** — Given a valid credential, a company, and a date range, When the agent asks for a productivity summary, Then the tool returns aggregated time totals (worked / manual / productive vs. not) for that range, optionally for one user.
- **AC6** — Given a valid credential, a company, and a date range, When the agent asks for a breakdown by application/website, Then the tool returns time spent per app/website category for that range, optionally for one user.
- **AC7** — Given a request with no Time Doctor credential header, When any tool is called, Then the call is rejected with 401 before any call reaches Time Doctor, and the error names the required header.
- **AC8** — Given a credential whose companies list has more than one entry, When a tool is called without specifying which company, Then the tool does not guess — it returns an error listing the available company ids/names so the caller can retry with one specified.
- **AC9** — Given two concurrent requests carrying two different customers' credentials, When both are in flight at the same time, Then neither response contains the other customer's credential, company data, or user/project/worklog data — per-request isolation holds under concurrency.
- **AC10** — Given Time Doctor's API returns a rate-limit response (429) or a server/network failure, When a tool call hits that condition, Then the tool returns a structured, typed error (`rate_limited` / `upstream_error`) rather than an unhandled exception or a raw pass-through of Time Doctor's response.

### Open questions

- Should v1 also expose absence/lateness and disconnectivity reporting? **Not blocking** — decided no for v1 (see "Decisions made by DEV01"); the one-line ask names time, projects, and productivity activity, not attendance. If this assumption is wrong, a follow-up ticket adds the extra tools without touching the v1 surface.

## Tech design

### Conclusion

Build `MSPbotsAIFramework/timedoctor-mcp` from scratch (SOP main line A): Python 3.12 + `uv` + FastMCP, stateless HTTP, one credential header (`X-Timedoctor-Token`, a Time Doctor v2 JWT), six read-only tools covering companies/users/projects/worklogs/activity-summary/activity-by-category, calling `https://api2.timedoctor.com/api/1.0`. First commit goes straight to `main` (no dev-lock needed for a brand-new repo per SOP A2); the dev leg registers it on INT with `/api/vendor-register` since the gateway does not know this vendor yet.

### Where the current implementation lives

Nowhere yet — `README.md:1-2` is the only file in the repo (see "Current state"). Everything in "Change list" below is new.

### Option analysis

- **Which Time Doctor API to integrate against**: v2 JWT (`api2.timedoctor.com`) vs. legacy v1.1 OAuth2 (`webapi.timedoctor.com`). Chosen: v2 JWT. Rationale and rejected alternative are in "Decisions made by DEV01" (credential-shape fit is the deciding factor, not feature coverage — both APIs expose equivalent read endpoints).
- **Credential shape**: a single pre-obtained JWT passed as a fixed header (chosen) vs. the service performing `email`+`password` (+TOTP) login itself and managing the resulting token (rejected — see "Decisions made by DEV01": this would mean handling a customer's Time Doctor password and persisting a token server-side, both at odds with the "Header-only, stateless" contract).
- **Company scoping**: optional `company_id` parameter with auto-resolve-if-single-company (chosen) vs. mandatory `company_id` on every call (rejected: worse ergonomics for the common single-company case) vs. silently defaulting to the first company returned (rejected: would route a multi-company account's data to the wrong company, a correctness bug masquerading as convenience).
- **Tool surface**: 6 focused, read-only tools covering the ticket's ask (chosen) vs. a 1:1 mirror of every Time Doctor v2 endpoint, including writes (rejected: pulls in payroll/directory-sync/user-management/edit-time endpoints nobody asked for, blows past "tools are capabilities, not endpoint mirrors", and adds destructive tools with no requirement backing them).

### Data & API contract

Credential header (declared in README, read in `middleware.py`):

| Header | Required | Meaning |
|---|---|---|
| `X-Timedoctor-Token` | yes | Time Doctor v2 JWT (`POST https://api2.timedoctor.com/api/1.0/login` with the account's email/password/TOTP returns `data.token`, valid 6 months). Sent upstream as `Authorization: JWT {token}`. |

Tools (all `readOnlyHint: true`, `idempotentHint: true`, names prefixed `timedoctor_`):

| Tool | Params | Upstream call | Returns |
|---|---|---|---|
| `timedoctor_list_companies` | — | `GET /companies` | `[{id, name}]` |
| `timedoctor_list_users` | `company_id?`, `filter?`, `page? (default 1)`, `limit? (default 50, max 200)` | `GET /users?company=&page=&limit=&filter=` | `{items:[{id, name, role}], page, limit, has_more}` |
| `timedoctor_list_projects` | `company_id?`, `page?`, `limit?` | `GET /projects?company=&page=&limit=` | `{items:[{id, name, status}], page, limit, has_more}` |
| `timedoctor_list_worklogs` | `company_id?`, `from? (ISO date, default today-6)`, `to? (ISO date, default today)`, `user_id?`, `page?`, `limit?` | `GET /activity/worklog?company=&from=&to=&user=&page=&limit=` | `{items:[{user_id, task_id, project_id, start, end, duration_s}], page, limit, has_more}` |
| `timedoctor_get_activity_summary` | `company_id?`, `from?`, `to?`, `user_id?` | `GET /activity/stats/summary?company=&from=&to=&user=` | `{from, to, worked_s, manual_s, productive_s, unproductive_s}` (field names adapted to whatever `stats/summary` actually returns; see Risks) |
| `timedoctor_get_activity_by_category` | `company_id?`, `from?`, `to?`, `user_id?` | `GET /activity/stats/category?company=&from=&to=&user=` | `{from, to, categories:[{name, seconds}]}` |

`company_id` resolution (AC8): omitted → `resolve_company_id()` calls `GET /companies`; exactly one → used; zero or more than one → `invalid_argument` naming the candidates. Never cached across calls.

Pagination: `page` defaults to 1, `limit` defaults to 50, hard-capped at 200 regardless of what the caller asks for (SOP A4 token-economy rule); passed through to Time Doctor's own `page`/`limit` query params.

Error envelope (AC7/AC10), same shape for every tool:
```json
{"error": {"code": "rate_limited", "message": "Time Doctor rate limit hit, retry after 30s", "retryable": true}}
```
`code` ∈ `not_configured` (never expected here — header is mandatory, enforced at 401) / `unauthorized` (Time Doctor 401/403) / `not_found` (Time Doctor 404, e.g. unknown `company_id`/`user_id`) / `invalid_argument` (bad params, or AC8's ambiguous-company case) / `rate_limited` (Time Doctor 429) / `upstream_error` (Time Doctor 5xx, timeout, network failure).

### Key flow / sequence

1. Gateway forwards the agent's call to `POST /mcp` with `X-Timedoctor-Token` set.
2. Middleware reads the header into a per-request `ContextVar`; missing → 401, nothing downstream runs (AC7).
3. Tool handler resolves `company_id` (explicit, or via `resolve_company_id()` — AC8).
4. Tool handler calls the relevant `api2.timedoctor.com` endpoint through `client.py`, which attaches `Authorization: JWT {token}` from the contextvar.
5. Response mapped: success → trimmed/paginated JSON per the contract above; Time Doctor error → `errors.py` envelope (AC10).
6. `finally` block resets the `ContextVar` — nothing about this request survives into the next one, on this or any other concurrent request (AC9).

### Non-functional

- **Statelessness / isolation (AC9)**: credential and company resolution live only in the per-request `ContextVar`; no module-level cache, no singleton HTTP client holding a token. One container serves many tenants concurrently — this is the property SOP §3.3/§3.4 calls a "law", not a preference. Verified by `tests/test_middleware.py::test_concurrent_requests_do_not_leak_credentials_across_tenants` (TC-TD-009).
- **Network robustness**: 5s connect / 30s read timeout, bounded retry+backoff on 429/5xx honoring `Retry-After`, single call budget < 120s, one `httpx.AsyncClient` per request (not shared/cached across requests).
- **Security**: token never logged, never written to disk, never placed in an environment variable; `gitleaks detect` run before handoff; no real credentials anywhere in the repo.
- **Multi-tenancy**: every tool call is scoped to the company resolved for that request's own token; no response ever includes data resolved from a different request's token (AC9).
- **Observability**: structured error envelope makes failure mode visible to the caller without needing server-side logs; `/health` is a local liveness probe independent of Time Doctor's availability.
- **Token economy**: list-style tools cap at `limit=200`, default `50`; responses carry only the trimmed fields listed in "Data & API contract", not Time Doctor's raw payloads.

Tier reference (`templates-design.md`, "How to size a Story Point" section): 0.5 = a single tool/endpoint tweak in an existing connector; 1 = a few related fixes in one connector; 2-3 = a new connector or a sizeable new capability with some unknowns; 5 = a new connector with heavy unknowns (OAuth, multi-step flows, unclear vendor docs) or multiple interacting systems.

### Risks & dependencies

- **No test account**: all unit tests run against mocked responses; the one case needing a live account is marked and does not block release (SOP "no test account is not a blocker"). Risk: a schema mismatch between the mocked fixtures (built from the published docs) and Time Doctor's real responses would only surface after a customer connects a real account; mitigated by keeping response mapping defensive (missing optional fields default to `null`/omitted rather than raising).
- **`stats/summary` / `stats/category` field names are inferred from the vendor's own doc summary, not from a captured real response** (no test account to capture one against) — the exact JSON keys in "Data & API contract" may need a small adjustment once the dev leg runs a request against a real or sandbox account; this does not change the tool's parameters or its AC, only internal field mapping.
- **Rate limits**: the current v2 docs do not state a numeric cap (the legacy v1.1 docs mention 5000 requests/hour); the retry/backoff design treats whatever Time Doctor returns as authoritative (429 + `Retry-After`) rather than hard-coding a number.
- **Token lifetime**: the JWT is valid 6 months and is not auto-refreshed by this service (no refresh-token flow exists for it per the docs); the customer must rotate the `X-Timedoctor-Token` value in their connector configuration before it expires. Documented in the README's header table; not something this service can or should mask.
- **No dependency on another in-flight ticket** and no gateway/control-plane change required — this is a self-contained vendor repo.

### Decisions made by DEV01

1. **Target API: Time Doctor v2 JWT (`api2.timedoctor.com`, documented at `timedoctor.redoc.ly`), not the legacy v1.1 OAuth2 API (`webapi.timedoctor.com`).** Why: the OAuth2 authorization-code/refresh-token flow would require this service to hold a per-tenant `client_id`/`client_secret` and persist refresh tokens server-side to keep working past token expiry — both conflict with the "credentials only from a per-request Header, service is truly stateless" contract (SOP §3.1/§3.3). The v2 JWT API lets each customer obtain their own long-lived (6-month) token once, out of band, and hand it to the connector as a fixed header — the same shape every other header-credential connector in this org uses. Alternative not chosen: v1.1 OAuth2.
2. **Credential is one header carrying a pre-obtained JWT (`X-Timedoctor-Token`), not email+password handled by the service.** Why: performing the login call ourselves would mean receiving and forwarding a customer's Time Doctor account password through the MCP layer — a materially worse security posture than a single opaque token, and it still would not solve the refresh/expiry problem (decision 1). Alternative not chosen: accepting `email`/`password` (+`totpCode`) headers and calling `POST /login` on the customer's behalf.
3. **v1 scope is read-only: companies, users, projects, worklogs, activity summary, activity by category.** Why: the ticket's one-line ask is "track" time/projects/activity — a reporting need. Nothing in the ticket or the linked third-party page (treated as reference only, per `mcp-track.md` §2.1) asks to create/edit time entries, manage payroll, invite users, or configure directory sync. Building those now would be speculative (YAGNI) and some (`edit-time`, user/project deletion) are destructive — adding them without a stated need would also cut against SOP A4's "write tools need a stated business necessity". Alternative not chosen: mirroring every v2 endpoint 1:1.
4. **`company_id` is optional on every tool; omitted → auto-resolve via `GET /companies` if there is exactly one, else an explicit `invalid_argument` listing the candidates.** Why: most Time Doctor accounts manage a single company, so the common case needs no extra parameter; multi-company accounts get a clear, actionable error instead of a silent guess that could route data to the wrong company. Alternative not chosen: making `company_id` mandatory everywhere (worse ergonomics for the common case), or defaulting to the first company returned (a correctness bug for multi-company accounts).
5. **`from`/`to` on the worklog and activity-stats tools default to the trailing 7 days (today-6..today, UTC) when omitted.** Why: keeps the tools usable for an agent that has not been told to compute a date range; 7 days matches the "how's the team doing lately" framing of the ask. Callers can always pass explicit dates for anything else. Alternative not chosen: requiring explicit dates on every call.
6. **Deferred out of v1 (not built now)**: absence/lateness reporting (`/users/totals`, a dedicated report), disconnectivity periods (`/activity/stats/disconnectivity`), time-entry edits (`/activity/edit-time*`), user/project/task CRUD, invitations, directory sync, payroll. Why: none are named in the ticket's one-line ask; adding them now would be speculative scope (YAGNI) and, for the write endpoints, adds destructive tools nobody asked for. If a future ticket needs one of these, it is an additive tool on top of this v1 surface, not a rework of it.

### Implementation notes relative to the tech design

- **`mcp.server.fastmcp.FastMCP` (the MCP Python SDK's bundled implementation), not the third-party `fastmcp` package.** Verified experimentally (`inspect.signature`) that only the SDK-bundled `FastMCP` exposes `transport_security` on its constructor; the third-party `fastmcp>=2` package never threads a `security_settings` object into its `StreamableHTTPSessionManager`, so SOP §7's "DNS-rebinding protection must be off" cannot be satisfied through it. Switching packages did not change any tool behavior or the dependency footprint grew (`fastmcp` pulled in `pydocket`/`redis`/`typer`/etc. that are unused here; `uv sync` dropped them once removed).
- **`/health` is registered via `FastMCP.custom_route`, not a separately `Mount()`-ed outer Starlette app.** `FastMCP.streamable_http_app()` already wires `lifespan=lambda app: self.session_manager.run()` on the one Starlette app it returns, and `custom_route` adds to the same app's route list -- so there is exactly one app, one lifespan, and SOP §7's "Mount() drops lifespan" failure mode (`RuntimeError: Task group is not initialized`) cannot occur because there is no `Mount()` in this design. Verified experimentally: `Mount()`-ing the MCP app under a second outer app reproduces exactly that `RuntimeError`; the `custom_route` design does not.
- **Credential middleware is a plain ASGI callable wrapping the app directly (`CredentialMiddleware(inner_app)`), not a `Starlette`/`Mount()`-based wrapper**, for the same lifespan-passthrough reason -- `scope["type"] != "http"` (i.e. `lifespan`) is forwarded to `self.app` unchanged.
- **`from_date`/`to_date`, not `from`/`to`.** `from` is a Python reserved keyword. The installed SDK's `ArgModelBase.model_dump_one_level()` dispatches validated arguments to the tool function using the pydantic field's *alias* (not its Python attribute name) as the keyword argument name, so exposing a schema property literally named `from` would still require a function parameter literally named `from` -- impossible in Python. Verified experimentally: a `from_: Annotated[str | None, Field(alias="from")]` parameter does produce a `"from"` property in the generated JSON Schema, but calling the tool raises `TypeError: x() got an unexpected keyword argument 'from'`. This is a wire-contract naming detail (SOP §13: not a tool rename/removal, this is the first version's own contract), not a change to any AC -- no AC names the literal parameter.
- **Company-scoped list/stat endpoints are read via a `data`-wrapped envelope** (`{"data": [...]}` or `{"data": {...}}`), inferred from the vendor's published docs per the design's noted risk (no captured real response). Field extraction (`_field`, `_extract_items` in `tools.py`) is defensive: it tries several plausible key spellings and falls back to `None`/empty rather than raising, per the design's mitigation.
- `timedoctor_list_worklogs` additionally filters the mapped results by `user_id` client-side (in case the vendor's `user` query parameter is not honored server-side) -- belt-and-suspenders, not a behavior change; the request still passes `user` upstream.
